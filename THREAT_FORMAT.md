# Threat format

Every threat in this repository has the same shape, so a reader can open any of them and find the same things in the same places, and so the README, the coverage matrix and the ATT&CK layer can be generated. `tools/validate_threats.py` enforces it on every push.

The model borrows from the strongest public detection repositories and adds what none of them combines:

| Borrowed from | Idea | Here |
|---|---|---|
| Splunk `security_content` | An *analytic story* groups detections around one threat, and every detection ships with attack data | One folder per threat; tests are built from the threat's own captures |
| OTRF Security-Datasets | Telemetry is a published artefact with metadata | `telemetry/<id>.json` + `<id>.yml` (window, host, event counts, SHA-256, what produced it) |
| Atomic Red Team | Small, safe, repeatable emulations | `emulation/`, behaviour only, never an exploit |
| Elastic `detection-rules`, SigmaHQ | Rules carry structured metadata and are validated in CI | `detection.yml` + the format gate, lint, and Microsoft's own Kusto compiler |
| MITRE ATT&CK Navigator | Coverage as a layer | One generated layer per threat, coloured by test result |
| **MTDF** | Every detection anchored on a **minimum truth**; reinforcement raises confidence but never defines the attack | The attack-surface matrix: one row per vector, its minimum truth, and what covers it |

## Layout

```
threats/<slug>/
├── README.md                 GENERATED - never edit by hand
├── threat.yml                metadata + the attack-surface matrix (the source of truth)
├── docs/
│   ├── tradecraft.md         how it works, stage by stage, and what each stage cannot avoid leaving
│   ├── hunting.md            broad hunts: estate baseline → leads → single-device timeline
│   ├── forensics.md          artefacts, where they live, what each proves; Sysmon vs Defender fidelity
│   ├── deployment.md         (optional) rollout order, populations, tuning knobs
│   └── lab-notes.md          (optional) the engineering journal: assumptions, findings, why each fix
├── emulation/
│   ├── README.md             needs, run, step → matrix row → why it is safe
│   └── <script>              behaviour-only reproduction for the lab VM
├── telemetry/
│   ├── <capture_id>.json     raw Sysmon export from the emulation (evidence + hunting dataset)
│   └── <capture_id>.yml      dataset metadata (generated by add_capture.py)
└── detections/<name>/
    ├── <Rule>.kql            the rule, lab build (every widened window marked // LAB: production uses X)
    ├── detection.yml         title, architecture, tactic, techniques, minimum truth, reinforcement, tests
    ├── test_<capture>.yml    GENERATED from detection.yml by add_capture.py
    └── fixtures_<capture>/   GENERATED: the capture converted to Defender tables
```

## threat.yml

| Field | Required | Values / notes |
|---|---|---|
| `name`, `slug` | yes | `slug` = folder name, lowercase-with-hyphens |
| `type` | yes | `tradecraft`, `malware`, `campaign`, `zero-day` |
| `status` | yes | `emerging` (days–weeks old), `active`, `historical` |
| `first_seen`, `platforms` | yes | |
| `cves` | zero-day | write `none assigned` until there is one |
| `summary`, `threat_model` | yes | `threat_model` is the behaviour-first argument: why the minimum truths hold whatever the exploit |
| `attack_surface` | yes | the matrix (below) |
| `variants` | | the variant catalogue: `{id, name, capture, emulation, description, benign?}` (below) |
| `references` | | `{title, url}`; primary sources (vendor research, advisories) first |

### The attack-surface matrix

One row per way the threat operates. Each row has `stage`, `vector`, `techniques` (ATT&CK IDs), `minimum_truth`, and **exactly one** of:

- `detections: [names]` — folders under `detections/` that cover it;
- `boundary: "reason"` — no endpoint telemetry can see it; say why rather than claim it;
- `planned: "Rule - anchor"` — known gap with a named fix.

Optional `cousins: [{name, url}]` links related detections elsewhere (for example in MTDF-Detection-Tests).

The README shows each row's status from the last test run: ✅ validated · 🟡 partly · ⏳ awaiting run · 🧪 awaiting telemetry · ❌ failing · ⚠️ boundary · 🔲 planned. The matrix can never claim more than the tests prove.

### Variants

The matrix says *which ways* the threat operates; the variant catalogue says *which concrete reproductions* prove it. Each variant lives in one capture. A benign variant (`benign: true`) is normal activity that every detection must stay silent on. Tests name the variants they cover, and the README draws a variant × detection matrix from the last run, so a reader sees at a glance which sensor catches which variant and that the benign workflow raises nothing.

Every threat should end up with at least three captures: **the main path**, **the variants**, and **a benign workflow**.

## detection.yml

| Field | Notes |
|---|---|
| `title`, `author` | |
| `architecture` | `Primitive collector`, `Router`, `Composite sensor`, `Behavioural chain`, `Composite (L3)` (MTDF architectures) |
| `tier` | `core` (the threat's main path) or `cousin` (the **Cousin Pack**: adjacent sensors that catch variants) |
| `deploy` | `{mode: index/triage/alert/hunt, defender, sentinel, alert, why}` - see [deployment-model.md](docs/deployment-model.md) |
| `tactic`, `techniques` | ATT&CK tactic slug and technique IDs |
| `minimum_truth` | one sentence; never `TODO` |
| `reinforcement` | what raises confidence, and what scores down |
| `data_sources`, `platforms`, `production_lookback`, `source_rule` | |
| `tests` | list of `{capture, variants, catches, expect, maturity?, known_issue?}`. `expect` takes `must_fire`, `row_count` (0 = must stay silent), `contains` (exact), `contains_like` (substring) |

## Rules for every threat

1. **Behaviour, not indicators.** No hashes, IPs or domains as the anchor. Indicators may reinforce.
2. **One minimum truth per detection**, in one telemetry domain where possible.
3. **Allowlists score down, never exclude**, unless the action is benign (lesson from the Scheduled Task masquerade bug in MTDF-Detection-Tests).
4. **Emulations are harmless**: dead local ports, `whoami` payloads, read-only public calls. Never an exploit, never real malware.
5. **Boundaries are documented, not hidden.**
6. **Every detection is tested** against a capture before the threat leaves `emerging`, and every alerting detection has a benign test that expects silence.
7. **Every rule output carries `Timestamp`, `DeviceId` and `ReportId`**, so it deploys as a Defender custom detection as well as a Sentinel analytics rule (the primitive collector excepted: it is an index).
